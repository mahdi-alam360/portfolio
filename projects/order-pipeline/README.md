# Order Pipeline

AI-assisted personal learning project, built with Codex in October 2026. Local Python/SQLite ETL on a tiny synthetic order fixture. Not employment experience, an AWS deployment, or production infrastructure. Review and run the source before discussing personal implementation decisions in an interview.

## Run

Python 3.12+, standard library only. From the repository root:

```sh
python projects/order-pipeline/pipeline.py --input projects/order-pipeline/orders.csv --database /tmp/orders-demo.db --output projects/order-pipeline/wwwroot/report.json
python -m unittest discover -s projects/order-pipeline -p 'test_*.py' -v
```

On Windows, use a writable local database path instead of `/tmp/orders-demo.db`. The fixture contains no customer information. Four valid rows and four rejected rows deliberately exercise the validation path.

## Data flow

CSV extraction -> strict column/date/region/money validation -> row rejection log -> transactional SQLite upsert -> SQL regional aggregates -> atomically replaced JSON report. Money is stored as integer cents. IDs use parameterized SQL, including quotes. Replay is idempotent by order ID; a new record with the same ID replaces its prior values. Duplicate IDs within one file are rejected after the first valid occurrence. Source SHA-256 and accepted/rejected counts record batch provenance. The output reports cumulative stored data and the current batch's rejection reasons separately.

Tests cover exact money, malformed records, duplicate rejection, repeat loads, corrected records, SQL-shaped IDs, unchanged database on schema errors and changed source provenance. GitHub Actions runs the tests and regenerates the sample report for reproducibility.

## Website

The portfolio serves a static report generated by Python, not a browser-run Python pipeline or a hosted database. It exposes no upload endpoint. The browser reads only the checked-in synthetic JSON. Run the CLI locally to process another fixture.

## Limits and tradeoffs

All input is loaded into memory; this is not streaming or large-data processing. Single-writer demo, no scheduler, retries, cloud storage, AWS, orchestration or monitoring. SQLite changes are transactional, and the report file is replaced atomically, but there is no distributed transaction between the database and JSON file. A report-write failure after a successful database commit requires rerunning the command. Report provenance describes the latest batch, not a full version history of each row. Fixed allowed regions and maximum amounts are demonstration rules, not real business requirements. No claim of enterprise ETL experience or production readiness.
